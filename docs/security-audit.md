# Security Audit — Edge Functions, secrets and authentication

Scope: every Supabase Edge Function in the repo, the callers of each, secret handling, the
sign-up/approval flow and the unsubscribe lifecycle. Findings were verified against the code **and**
reproduced in a real Postgres + GoTrue + PostgREST stack (not by reading SQL alone).
Companion: [`rls-audit.md`](rls-audit.md) (table-level authorization).

## 2. Confirmed defects and fixes

| ID | Severity | Defect (confirmed) | Fix | Regression test |
|---|---|---|---|---|
| S-1 | **Critical** | `send-email` performed service-role writes and sent provider email for **any caller** (no authn/authz); `CORS: *` | `_shared/auth.ts` (`authenticate`, `requireStaff`): bearer required; token validated by the auth server; account must be `active`; staff = admin/coordinator or `notifications.send`; service key accepted for internal callers; body-supplied roles ignored; input validation (400 not 500); generic 500 messages; CORS allow-list via `ALLOWED_ORIGINS` | `_tests/security_test.ts` (unauth → 401, garbage/forged/non-bearer JWT → 401, member → 403 on every action, pending "admin" → 403, role-in-body ignored, admin/coordinator/delegate/service → 200, exact key match) and `_tests/integration_test.ts` against real GoTrue (incl. a JWT claiming `service_role` signed with a wrong secret → 401) |
| S-2 | **Critical** | `process-scheduled-emails` had no authentication at all | `x-cron-secret`/`CRON_SECRET` (`_shared/cron.ts`); POST only; fails closed if unset; atomic claim so overlapping runs cannot double-send; failures release the claim | missing → 401, wrong → 401, user JWT or service key is **not** a substitute → 401, correct → processed once, unset/weak secret → 503 (unit + real-DB) |
| S-3 | **High** | Unsubscribe token was `btoa(JSON)`: anyone could unsubscribe any member (and the client built it, so no secret could exist). The `type` query parameter also overrode the payload | Tokens are now `base64url(payload).base64url(HMAC_SHA256(payload, UNSUBSCRIBE_SECRET))`, generated **server-side** in `send-email`; verified with a constant-time comparison **before** the payload is trusted; payload re-validated (UUID + known type); `type` param ignored; client no longer builds tokens (placeholder `{{unsubscribe_url}}` replaced server-side); `List-Unsubscribe` + one-click `POST` (RFC 8058) added | round-trip; legacy unsigned token, malformed, tampered payload, tampered/extended signature, wrong secret, empty secret all rejected; endpoint changes nothing on rejection; client bundle exposes no token builder |
| S-4 | **Critical** | Anyone could register as `coordinator`: `handle_new_user` copied `raw_user_meta_data->>'role'` (reproduced on the migration chain) | trigger hard-codes `role='member'`, `status='pending'`, ignores metadata | `rls.test.mjs › client-supplied role/status metadata is ignored`; SQL test asserts trigger behavior |
| S-5 | **Critical** | Any user could set their own `role`/`status`/`cell_id` via PostgREST (`profiles_update_own`); `leaders_manage_profiles` let any cell leader edit any column incl. `role` | `profiles_guard` trigger + narrowed policies (see `rls-audit.md`) | 9 tests in *sign-up and approval* / *active member profile boundaries* |
| S-6 | **High** | `is_devotional_admin()` trusted `user_metadata.role` (editable by the user via `auth.updateUser`) | now `has_admin_permission('devotionals.manage')` (DB role/permission tables) | `changing user_metadata.role … does not grant devotional/admin rights` |
| S-7 | **High** | Committed `create-test-users.js`: production project URL + anon key, weak shared test passwords, and it only worked *because of S-5* | file removed. **Action for owners:** if those `+testcoord/+testleader/+testmember` accounts exist in production, delete or rotate them (UNVERIFIED) | — |
| S-8 | Medium | Send path ignored `email_preferences` entirely (no suppression after unsubscribe) | resolve member (explicit id or by email), honour `opt_out_all` and the per-type column (incl. `weekly_digest` default-off), log `status='suppressed'` | unit + real-DB: unsubscribe → next send suppressed and logged; scheduled mail suppressed |
| S-9 | Low | `unsubscribe` echoed unescaped text into HTML; Supabase serves function HTML as `text/plain` on `*.supabase.co` | output escaped; if `PUBLIC_APP_URL` is set the browser is redirected (303) to `/email-preferences?unsubscribed=…` so the user still sees a real page | redirect + escaping test |

## 3. Legacy unsubscribe links

Old links (`btoa(JSON)`) are **rejected** — no compatibility mode was added. Tradeoff: previously delivered
emails will show "invalid link" with a pointer to the in-app preferences page. Accepting unsigned tokens even
temporarily would keep S-3 exploitable, and `send-email` could not legitimately have delivered mail before this
change except to people an operator invoked it for, so the blast radius of breaking old links is small.

## 4. Authentication / approval flow (summary)

`signup → profiles(status=pending, role=member) → approver sets status=active → login → permissions from DB`.
Enforced **in the database** (not only the UI): a pending/rejected account can read only its own profile row and
cannot write anything; it cannot approve or promote itself; only a coordinator changes roles; cell leaders can
approve members only (not staff, not themselves). Verified by API tests and by a real-browser run
(`e2e/real-backend.spec.ts`).
