The Problem

Members were getting
lost in the cracks.

BLW York had 23 active members across multiple cell groups — and no reliable way to track any of them. Contact info lived in group chats, spreadsheets, and people's heads.

✗ No centralized system — contact info scattered across chats, spreadsheets, notes
✗ Members forgotten — new contacts logged but never followed up on
✗ Activity invisible — devotional reading, habit progress, attendance untracked
✗ Leadership blind spots — coordinators couldn't see who was struggling or thriving
✗ Inconsistent process — every cell leader tracked things differently
✗ No accountability — follow-ups happened ad-hoc, dependent on one person's memory
✗ Data silos — information locked per cell, invisible across the ministry
✗ Growth invisible — no way to measure spiritual engagement or development trends

The downstream cascade

  • Contacts not followed up on  — lost evangelism opportunities
  • Members disengaging  — not noticed until they stopped coming
  • Meetings scattered across platforms  — confusion, no-shows
  • Prayer requests forgotten  — pastoral care gaps
  • Attendance data lost  — can't identify at-risk members
The Solution

A complete membership
management platform.

I designed and built an app that gives leaders real-time visibility into member engagement, and gives every person in the ministry a clear, organized workflow for outreach and growth.

01

Member Directory & Role-Based Access

Centralized member profiles with four permission tiers: Coordinator, Admin, Cell Leader, and Member. Each role sees exactly what they need — cell leaders see their group's data, coordinators see everything. A member approval workflow gives cell leaders control over who joins.

Supabase RLS Multi-tenant Approval workflow
Solved: Leadership blind spots and inconsistent access control across the ministry.
02

Contact Management (CRM)

The core of the app. Log outreach contacts with status, tags, notes, and assigned follow-up owner. Bulk-import up to 50 contacts from CSV. Reassign follow-ups when someone can't continue. Move contacts between cells when they relocate. Archive unresponsive contacts without data loss.

Bulk CSV import Follow-up tracking Status workflow Contact reassignment
Solved: No more lost contacts, unclear responsibility, or ad-hoc follow-up processes.
03

Member Growth Tracking

Daily devotionals delivered as PDFs with per-member view tracking. Habit tracking with daily check-ins, visual streaks, and personal statistics. A testimony log where members share faith stories with community comments and encouragement.

PDF devotionals Habit streaks Testimony feed Engagement analytics
Solved: Spiritual growth metrics were invisible. Now leaders see who's reading, who's tracking habits, and who's sharing.
04

Leadership Dashboard & Reports

Coordinators land on real-time stats: members per cell, contacts logged, devotional engagement, recent activity feed. Reports answer "which cells are most engaged?" and "who's not attending meetings?" — with CSV export for deeper analysis.

Real-time dashboard Engagement reports CSV export Activity feed
Solved: Leadership decisions were gut-feel. Now they're data-driven.
05

Meetings, Notifications & Communication

Schedule meetings with Zoom integration, in-app RSVP, and automatic email reminders at 8 AM and one hour before. Push notifications keep members informed. Weekly Messages deliver coordinated leadership communications across email and push. Daily Confessions build community accountability.

Zoom integration SendGrid email Web Push (VAPID) RSVP tracking
Solved: Meetings scattered, reminders forgotten, attendance unpredictable.
06

Accessibility, Mobile & PWA

WCAG 2.1 AA compliant throughout — keyboard navigation, screen reader support, contrast ratios. Mobile-first design with dark mode. Installed as a PWA for offline devotional reading when there's no signal. Multi-language scaffold ready for growth.

WCAG 2.1 AA PWA / offline Dark mode i18n scaffold
Built right: Accessibility from day one — not retrofitted as an afterthought.

Technical Execution

Architecture decisions
that were made deliberately.

Every layer of the stack was chosen against a specific constraint — not defaulted to.

Layer Technology Why this, not the alternative
Frontend React 18 + TypeScript Strict mode catches bugs before runtime; self-documenting types reduce onboarding cost. Considered Vue — less hireable, ruled out.
Styling Tailwind CSS Utility-first keeps component styles colocated with structure. No separate CSS files to maintain.
Database Supabase (PostgreSQL) Row-Level Security enforces data separation at the database level — not in application code where it can be bypassed. Firebase considered but lacks RLS.
Auth Supabase Auth (JWT) Built-in, integrates with RLS policies directly. No separate auth service to sync.
Backend logic Supabase Edge Functions Serverless — zero DevOps overhead at current scale. SendGrid and Zoom secrets stay server-side, never in the browser.
Hosting Vercel Push to GitHub → auto-deploys. Preview environments on every branch. AWS was overkill for this scale.
CI/CD GitHub Actions Automated tests run on every PR. Nothing merges without passing TypeScript and test suites.
Integrations Google Drive · SendGrid · Zoom Each solves a specific real workflow gap — not added for technical interest.
Why Row-Level Security over application-level access control?
RLS policies enforce cell data separation at the database layer — a bug in application code can't accidentally expose another cell's contacts. This is the same pattern enterprise multi-tenant SaaS uses. It also means any future API surface (mobile app, third-party integrations) inherits the same security model for free.
Why TypeScript strict mode throughout?
Strict mode prevents an entire class of runtime errors — null dereferences, wrong API shapes, missing fields on database responses. Combined with Supabase's generated types, the compiler catches mismatches between the database schema and the UI before they reach users.
Why build a PWA instead of a native app?
Members use the app on phones, often with unreliable campus Wi-Fi. A PWA installs from the browser, caches the daily devotional offline, and delivers push notifications — without the overhead of App Store distribution or maintaining a separate codebase.

Lessons Learned

What I'd do the same.
What I'd do differently.

Honest retrospective — not just what sounded good at the end.

What went well

  • Regular check-ins with org leaders shaped features before I built the wrong thing
  • Built the CRM core first — everything else became easier once contacts worked
  • Accessibility from day one, not retrofitted at the end
  • TypeScript strict mode caught every database shape mismatch early
  • RLS security policy designed up front — not bolted on after

What I'd do differently

  • Design mobile-first, not responsive-last — a few screens needed rework
  • Get feedback from real members earlier, not just leadership
  • Add real-time collaboration on shared records from the start
  • Track in-app usage analytics from day one (can't instrument retroactively)
  • Build an onboarding flow — first-time users needed more guidance than I gave them
